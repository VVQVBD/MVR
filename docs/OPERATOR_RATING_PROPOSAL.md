# Предложение: рейтинг и приоритет операторов

Статус: **пилот (этап 1 из плана ниже) реализован и покрыт тестами** — см. README.md, раздел «Пилот рейтинга операторов». Формула баллов — вариант 2; критерии оценки — без изменений; премия — фиксированная по месту в рейтинге (все три решены командой). Этапы 2–4 (форма заявки, фото, авто-приоритет и выбор района) — ещё черновик, ждут отдельного «начинаем». Решены 4 исходные развилки:

1. **У операторов — личный вход** (email/телефон + пароль), как у остальных ролей — новая роль `operator` в RBAC, по аналогии с `client`/`subcontractor` (привязка к `Operator`, не к компании).
2. **Форма заявки — новый слой поверх договоров**, а не замена текущей модели. Разовая заявка (`CleaningOrder`) может ссылаться на существующий `Contract`/`FacilityObject`, если это постоянный клиент, либо быть самостоятельной.
3. **Фото — в бекенде по-настоящему**: файл на диске сервера (`backend/storage/order-photos/`, путь — в БД), раздаётся как статика через FastAPI. Для пилота этого достаточно; в проде — переезд на S3-совместимое хранилище без смены API (меняется только реализация записи файла).

## 0. Что это меняет в продукте

Сейчас в системе нет понятия «оператор» как сущности — есть только обезличенный `operator_code` в отметках смен (`shift_reports`), без аккаунта, истории, рейтинга. А разовых заявок на уборку с выбором площади/качества/бригады тоже нет — есть только долгосрочные Б2Б-договоры (`Contract` → `FacilityObject`) с фиксированным ежемесячным тарифом и постоянным графиком.

Описанная вами механика (приоритет → больше заказов → баллы лояльности → рейтинг → премия, выбор района лидерами, обнуление раз в квартал) ближе к **модели разовых заказов с распределением по рейтингу**, чем к текущей модели «один договор — один фиксированный объект». Это не проблема, а развилка: см. вопрос **Q3** ниже — она определяет объём работы.

## 2. Формула рейтинга и приоритета (рекомендуемый вариант)

Простой прозрачный счётчик баллов — в духе остального проекта (детерминированный расчёт, а не «чёрный ящик»):

```
за каждый выполненный заказ:
  баллы_за_заказ = базовые_баллы(площадь, качество)         # больше объём/сложнее уборка — больше баллов
                  + баллы_за_оценку(средний балл клиента)     # напр. (балл − 5) × коэффициент: ниже 5 — баллы в минус
  баллы_лояльности += баллы_за_заказ

приоритет_оператора = место в сортировке по баллам_лояльности внутри текущего квартала (по убыванию)
```

- Чем выше приоритет — тем раньше оператору предлагаются новые заказы (и, по вашему пункту про район, тем раньше он выбирает район в следующем периоде: более дорогой район → бо́льшая площадь → больше оплата).
- Низкая оценка **обязательно** сопровождается комментарием клиента/менеджера — без текста низкую оценку поставить нельзя (как и остальные находки в проекте: без обоснования цифра не принимается).
- Раз в квартал: `OperatorPeriodStats` фиксируется (снэпшот для истории и премии), баллы лояльности обнуляются — у всех новый старт.
- Раз в месяц: по текущим (ещё не обнулённым) баллам считается премия — формула премии открытый вопрос, см. **Q5** в вопросах ниже по тексту ответа.

Альтернатива (на выбор команды): рейтинг как взвешенное среднее оценок клиентов за период, а баллы лояльности — отдельно, только для премии. Проще объяснить жюри «средним баллом», но хуже показывает активность (оператор с одним заказом на 10 баллов обходит оператора с 20 заказами на 9).

## 3. Форма заявки клиента/менеджера (ваш список полей)

1. Город, сегмент помещения — переиспользовать справочники из `/api/v1/calculator/norms` (они уже есть).
2. Площадь, м² → квадратура определяет цену — переиспользовать нормативы `09_Нормы_для_сметы.xlsx` и логику `app/services/estimate.py`, но добавить **разовый** (не ежемесячный) тариф за один выезд.
3. Качество уборки: поверхностная / средняя / генеральная — множитель к цене (нужно завести коэффициенты — нет в текущих нормативах пакета, спросить у организаторов или задать самим).
4. Бригада: 1–2 оператора / команда / «другое» (свободное число) — поле `team_size_mode` + `custom_operator_count`.
5. Свободное поле пожеланий/замечаний — текст, уходит в заказ и к оператору.

## 4. Фото после уборки

Загрузка файла к заказу, привязанному к оператору. Без оценки ИИ сейчас — поле `ai_review_status` в модели сразу заложено как `not_evaluated`, чтобы на питче честно сказать «функция оценки по фото — в разработке, сейчас фиксируем факт уборки». Где хранить файл — см. **Q4**.

## 5. API (эскиз)

```
POST /operators                          создать оператора (персонал)
GET  /operators/ranking?period=2026-Q4   таблица рейтинга для менеджера
POST /orders                             заявка на уборку (клиент/менеджер)
POST /orders/{id}/assign                 назначить оператора(ов) — по приоритету или вручную
POST /orders/{id}/photos                 фото после уборки
POST /orders/{id}/rating                 оценка 1–10 по критериям + комментарий
POST /operators/ranking/close-month      закрыть месяц — посчитать премию
POST /operators/ranking/reset-quarter    обнулить баллы лояльности
```

## 6. Этапы (от простого к сложному)

1. ✅ **Пилот — реализовано.** `Operator` (+ личный вход, роль `operator` в RBAC), `OperatorRating` (1–10 по 4 критериям, комментарий обязателен при низком балле), лента баллов `OperatorPointsEntry`, рейтинг и фиксированная премия за квартал. Бекенд + RLS + 20 тестов. Показывать можно через `/docs`, `GET /api/v1/operators/ranking` и ручной сценарий из README — отдельного экрана фронтенда для этого пока нет (можно добавить карточку рейтинга в «Закрытие месяца», это уже следующий, не самый большой шаг).
2. `CleaningOrder` с формой заявки, фото (файл на диске) и ручным назначением оператора менеджером.
3. Автоматический приоритет при назначении + выбор района лидерами + ежеквартальное обнуление + расчёт премии.
4. Экраны: форма заявки (клиент/менеджер), таблица рейтинга (менеджер), личный кабинет оператора (вход, свой рейтинг, свои заказы).
